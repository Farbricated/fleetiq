# FleetIQ: Hackathon Q&A Prep

This document contains anticipated questions from the judging panel, paired with verified, policy-backed answers from the project's Architectural Decision Records (ADRs) and codebase realities.

## 1. Product & Scope Decisions

**Q: Why doesn't this have a Map View to track assets?**
**A:** We explicitly deferred a map view because it is layout-fragile and redundant. As noted in ADR-001, a sorted asset table achieves our "SPOT" narrative beat with zero risk, instantly bubbling the most critical issues to the top. A map adds no story beat that isn't already covered more efficiently by our intelligence dashboards.

**Q: A lot of teams are building AI Copilots. Why isn't there a conversational AI here?**
**A:** We intentionally cut the AI Copilot to preserve the core value proposition of our product: human agency. FleetIQ is designed to tee up decisions, not make them autonomously. Unpredictable LLM latency and hallucination risks would undermine the trust we are building in the "ACT" beat (Beat 3), where manager action is the core narrative.

**Q: Are the natural-language summaries on the Asset 360 page generated by an LLM?**
**A:** No. They are deterministic strings generated by our backend rule engine. We chose this approach to deliver high impact for the "EXPLAIN" beat (Beat 2) without the latency or unreliability of an LLM. It carries narrative weight but is 100% reliable.

## 2. Engineering & Architecture

**Q: Where is the data coming from? Are you actually running simulations?**
**A:** The underlying challenge dataset consists of 7 rows of snapshot data, which we load into a fully relational PostgreSQL database (23 tables). All analytics use deterministic, rule-based scoring (like our Weighted Moving Average for demand forecasting) rather than black-box ML models. 

**Q: How do you handle the "What-If" prediction panel in the UI? Is that live?**
**A:** We explicitly removed the "What-If" simulation panel from the final build. We decided in ADR-001 that building a live dynamic simulation engine risked breaking the core flow right before the deadline. We preferred to ship a clean, fully-functional WMA forecasting engine rather than leaving a static "ILLUSTRATIVE ESTIMATE" mock in the UI that could undermine trust in the rest of the application.

**Q: How do you calculate the impact of an action on the Impact page?**
**A:** When a recommendation action is taken, the backend generates an `ImpactRecord` metric (Projected Utilization Improvement) based on the candidate's allocation score. Because this hasn't been realized in the field yet, our frontend strictly enforces the display of an **ILLUSTRATIVE ESTIMATE** provenance pill, ensuring we never misrepresent derived data as ground truth.

**Q: How easily can another developer run this stack?**
**A:** Very easily. We provide a single-click native script (`start_demo.sh`) for WSL/Linux environments, as well as a complete `docker-compose.yml` that containerizes the PostgreSQL database, FastAPI backend, and React/Vite frontend for seamless cross-platform deployment.
